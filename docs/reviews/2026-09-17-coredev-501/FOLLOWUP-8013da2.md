# Повторное ревью 8013da2

Проверка выполнена на изолированном worktree точного коммита. Текущие правки соседней сессии не проверялись и не изменялись.

## P1: guard не распознаёт замену задачи без restore

ASSOC[] с A → TEXT[] без drain → PERSON[]; пользователь записывает B; Restart первой задачи удаляет B (`[]` вместо `[7L]`). Строка исходного backup остаётся `backup=true`, поэтому `isUndoneByARestore` пропускает задачу. Проверка только исходного backup не доказывает актуальность целевой колонки. Нужна идентичность/поколение перехода и запрет побочных эффектов устаревшей задачи.

## P1: оставленный снимок смешивается со следующим

ASSOC[] с A → TEXT[] (drain) → ASSOC[]; пользователь записывает B; drain пропускает восстановление A. Затем TEXT[] (drain) → ASSOC[] (drain): возвращаются A+B (`[2L, 4L]` вместо `[4L]`). `backupAssocsOf` дописывает B к оставшемуся A под повторно использованным columnMetaId.

Оставлять снимок как архив можно только отдельно от текущего восстанавливаемого поколения. Простое сохранение под прежним ключом не является безопасным архивированием. Удаление пропущенных связей требует отдельного решения о гарантиях восстановления; оно не эквивалентно сохранению плана Б.

## P2: prepare(null) не останавливает перенос

ASSOC[] → TEXT[] (drain) → ASSOC[] без drain → TEXT[]; Restart устаревшего restore. Guard срабатывает, но `DbBatchTaskEngine.prepareRun` трактует null как отсутствие оценки числа строк, затем вызывает `processBatch`. Восстановление пытается записать Long[] в TEXT[], транзакция откатывается, errorCount становится 1 и задача уходит в backoff.

Проверки только отсутствия связей недостаточно: их отсутствие объясняется rollback. Репродуктор дополнительно проверяет errorCount. Нужен явный пропуск/завершение устаревшей задачи либо защита всех callback, включая `processBatch` и `onFinish`; один guard в prepare недостаточен.

## Остальные вопросы

- **Признак `!backup`:** в обычных путях миграции restore действительно переводит существующий backup в live. Обратное неверно: `backup=true` не доказывает актуальность задачи. При повторных переходах строка также может снова стать backup.
- **Конкурентность:** одна транзакция не делает пару SELECT/INSERT взаимоисключающей с другой транзакцией. Текущая проверка пустоты не блокирует запись, `createAssocs` допускает разные target id. Нужна общая с обычными мутациями сериализация по записи либо атомарная проверка версии с откатом всех side effects. Повторная незаблокированная проверка лишь сдвигает гонку. Этот пункт проверен по коду, конкурентный тест здесь не выполнялся.
- **Матрица:** сравнение физической колонки усилено правильно. Для ассоциаций сравнение количества остаётся пробелом: необходимо сравнить target id, порядок, child, created и creator для всех связей, включая элементы после десятого. Это часть исходного замечания P2. Хороший контроль — подмена одиннадцатого target при неизменном числе связей.
- **Комментарии:** новый KDoc `isUndoneByARestore` утверждает, что задача остаётся осмысленной при любых последующих сменах модели, кроме restore. Первый репродуктор опровергает это. Оставить краткий точный контракт вместо такого обоснования.
