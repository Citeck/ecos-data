# Ребёнок сохраняет `_parent` на время, пока связи припаркованы

Решение пользователя от 2026-09-18, по итогам разбора: «давай вариант с оставлением `_parent` и
`_parentAtt`». Отменяет прежнее поведение выпущенной `1.73.0`, где уход атрибута из группы
ассоциаций снимал у детей back-reference.

## Почему прежнее поведение отвергнуто

Постановка пользователя: ноды платформы могут храниться в любом микросервисе, связи между ними
дублируются в каждой задетой схеме, и код не должен предполагать, что связанные сущности лежат в
одной схеме. Плюс: «дочерние ноды оставлять висеть вечно без возможности до них дойти в интерфейсе —
так себе поведение».

Прежний release нарушал ровно это, тремя разными способами.

1. **Сироты.** Отпущенный ребёнок не назван никем: до него не доходит ни `_parent`-предикат, ни
   интерфейс, который показывает детей через родителя. Пока администратор держит атрибут текстовым —
   а это может быть навсегда — запись недостижима.
2. **Окно world-readable.** `DefaultDbPermsComponent` отдаёт записи с пустым `_parent`
   `canRead = true` и `authoritiesWithReadPerms = [EVERYONE]`. Смена типа колонки публиковала всех
   детей всех ограниченных родителей.
3. **Единственный код миграции, требовавший локальности.** `DbAssocGroupDeparture.releaseChildren`
   писал две колонки ребёнка напрямую через `DbDataService`, а `childTableOf` возвращал `null` для
   `childRef.getAppName() != schemaCtx.dataSourceCtx.appName` — ребёнок в другом приложении не
   отпускался вовсе (`log.error` и висящий `_parent`). При этом в списке `childIds` передавались
   `ed_record_ref` id **мигрируемой** схемы, а фильтр `__ref_id IN childIds` исполнялся в схеме
   ребёнка, где своё пространство id: для ребёнка в другой схеме того же приложения выборка либо не
   находила строку, либо попадала в чужую. Внутри одной схемы числа совпадают, поэтому тесты были
   зелёными.

Всё остальное в миграции уже федеративно: `takeChildren` и `childrenThisRecordMayTake` ходят через
`RecordsService`, зеркала связей в чужих схемах ведёт `DbRecordsRemoteActionsClient`.

## Что теперь

**1. Departure не трогает `_parent`/`_parentAtt`.** Из `DbAssocGroupDeparture` удалены
`releaseChildren`, `childTableOf` и `ChildTable` — 190 строк, единственное место прямой записи в
таблицу ребёнка. Уход по-прежнему копирует связи в `ed_associations_backup`, удаляет их с
`force = true` и уведомляет соседние приложения.

**2. Удаление ребёнка применяется к снимку, а не к атрибуту.**
`RecMutAssocHandler.forgetParkedChildLinks` вызывается до извлечения операций мутации: если мутация
несёт `MUTATION_FROM_CHILD_FLAG`, а названный атрибут больше не child-ассоциация, цели удаляются из
`ed_associations_backup` (`DbAssocBackupService.forgetTargets`), а сама операция снимается с мутации,
чтобы не править пользовательский текст. Признак законности уведомления — тот же запрос: если
припаркованных строк нет, `validateChildAssocs` отказывает, как отказывал раньше.

Тот же путь закрывает и переподчинение: новый родитель заставляет старого получить `att_remove`, и
снимок отпускает цель — возврат типа не отнимает ребёнка у того, кому его отдал пользователь.

**3. Удаление родителя забирает припаркованных детей.** Каскад `DbRecordsDeleteDao` шёл по
`ed_associations (child = true)`, где во время окна строк нет. Добавлен вызов
`takeParkedLinksOf(refId)`: одно чтение снимка отвечает сразу на оба вопроса — кого из детей забрать
(через федеративный `recordsService.delete`) и что удалить, потому что записи больше нет. Цена на
обычной установке, где ни один атрибут не уходил из группы: **один индексный запрос на удаление
записи**, возвращающий пусто.

**4. Undo заявки отпускает, а не удаляет.** Найден и закрыт живой дефект ветки:
`undoLinksWrittenForRecord` звал `updateParentRefOfChildren(add = false)`, а это не «снять
back-reference», а **удалить ребёнка** — `DbRecordsDao.mutate` читает `_parent = null` под
`MUTATION_FROM_PARENT_FLAG` как «родитель отпустил ребёнка». То есть фоновая задача, потерявшая
заявку на строку, удаляла пользовательскую запись. Добавлены `DbRecordsControlAtts.RELEASE_CHILD` и
`RecMutAssocHandler.releaseChildren`, undo пользуется ими. Прежний тест этого не ловил: он
утверждал `_parent?id` пуст, что верно и для удалённой записи.

**5. Индекс на `ed_associations_backup (__source_id)`.** Каждое удаление записи теперь спрашивает эту
таблицу по одному только источнику, а оба индекса `1.73.0` начинаются с `__column_meta_id`. Без индекса — полный скан на каждое удаление. Индекс добавлен в
`DbAssocBackupEntity`, а для уже существующих таблиц заведена схемная миграция
`AddAssocBackupSourceIndex` (версия 12, `NEW_SCHEMA_VERSION` поднят): реконсиляция схемы строит
индексы только для **новых колонок**, поэтому индекс, добавленный к существующей таблице, сам по
себе не доезжает никуда.

## Тесты

Новые и переписанные, оба бэкенда:

| тест | что фиксирует |
|---|---|
| `aDepartureKeepsBothHalvesOfTheBackReferenceTest` | обе колонки остаются на месте |
| `aChildIsStillDeletableWhileItsLinkIsParkedTest` | ребёнок удаляется, уведомление не падает |
| `aChildDeletedWhileItsLinkIsParkedIsNotLinkedBackByTheReturnTest` | снимок забыл цель; проверено прямым чтением `ed_associations_backup` |
| `aChildTakenByAnotherParentWhileItsLinkIsParkedIsNotTakenBackByTheReturnTest` | переподчинение переживает возврат типа |
| `deletingAParentWhileItsChildLinksAreParkedTakesTheChildrenWithItTest` | каскад по снимку |
| `aChildAdoptedByALostClaimIsReleasedRatherThanDeletedTest` | undo отпускает, а не удаляет |
| `aChildOfARestrictedParentStaysRestrictedWhileItsLinkIsParkedTest` | окна world-readable больше нет |
| `upgradeFrom11To12AddsTheSourceIndexToTheAssocBackupTableTest` | индекс появляется на существующей таблице |

Каждый проверен на честность: production-правка временно отменялась, тест краснел, правка
возвращалась. Тест `aChildDeletedWhileItsLinkIsParkedIsNotLinkedBackByTheReturnTest` в первой
редакции проходил и с отменённой правкой — усилен прямым утверждением о содержимом снимка.

Полный прогон (после всех правок этой темы и следующей): `ecos-data-sql` 140/0/0,
`ecos-data-sql-pg` 948/0 (1 skipped), `ecos-data-inmem` 1825/0 (88 skipped).

## Что осталось открытым

- **Сироты, оставленные выпущенной `1.73.0`.** У установок, где уход уже отработал, дети лежат с
  пустым `_parent` и припаркованными связями. Возврат типа их чинит (`takeChildren` пишет
  back-reference — этот путь остался и покрыт тестом с ручной постановкой такого состояния), но
  установка, где тип не вернут, остаётся с сиротами. Отдельный ремонтный шаг (пройти
  `ed_associations_backup` и восстановить `_parent` там, где ребёнок его лишился) не реализован —
  нужно решение пользователя.
- **Зеркало связи в чужой схеме не знает о дочерности.** `UpdateRemoteAssocsAction.execute`
  создаёт зеркальную строку с `createAssocs(..., child = false, ...)` — жёстко. И
  `restoreAssocsMeta` применяется только в своей схеме, поэтому у зеркала после возврата новые
  `__created`/`__creator`. Это шире COREDEV-501.
