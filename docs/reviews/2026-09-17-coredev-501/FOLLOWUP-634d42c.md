# Ревью точного 634d42c

Проверено в отдельном worktree без изменений production-кода. Прежние три репродуктора проходят. Найдены три дополнительных дефекта.

## P1: пустой следующий снимок не заменяет старый

ASSOC[] с A → TEXT[] (drain) → ASSOC[]; пользователь записывает B; drain пропускает старый A. После завершения задачи пользователь очищает B. Затем TEXT[] (drain) → ASSOC[] (drain) возвращает A вместо пустого значения.

`DbAssocGroupDeparture.run` обходит только живые связи, поэтому запись без связей не попадает в `backupAssocsOf`. Кроме того, этот метод сразу возвращается при пустом результате. Замена снимка учитывает непустое множество, но не пустое. Это не очистка во время переноса: пользователь очистил значение после завершения задачи.

Для непустых записей разные окна сами по себе не требуют накопления: метод читает все связи переданных sourceIds, а удаление предыдущего снимка ограничено этими sourceIds. Проблема — полнота набора источников и обработка пустого снимка.

## P1: восстановление прежнего target id оживляет старую задачу

ASSOC[] с A → TEXT[] (задача T, без drain) → PERSON[] с B → TEXT[] (restore прежней текстовой колонки, без drain). Живой id снова равен `T.targetColumnMetaId`. Restart T заменяет исходный ASSOC-backup A на PERSON-связь B: `[7L]` вместо `[2L]`.

Тест отдельно подтверждает совпадение id и исходное содержимое backup до запуска. Идентичность переиспользуемой колонки не является идентичностью перехода. Нужен токен поколения миграции, который меняется при каждом заменяющем переходе, включая restore, либо равноценный способ навсегда отличать заменённую задачу.

## P2: admin cancel/restart обходит остановку в prepare

Детерминированный PostgreSQL-тест задаёт порядок независимых транзакций через обёртку реального handler:

1. Engine прочитал PENDING перед prepare.
2. Администратор отменил задачу отдельной транзакцией.
3. Настоящий `DbColumnMigrationHandler.prepare` распознал устаревший target, но его `cancel()` увидел CANCELLED и вернул false, не выполняя UPDATE.
4. Администратор перезапустил задачу отдельной транзакцией: снова PENDING.
5. CAS в `prepareRun` совпал; engine вызвал processBatch один раз, хотя guard отказал в выполнении.

Успешная собственная отмена внутри prepare удерживает блокировку строки до завершения транзакции. Но ветка `cancel=false` на уже отменённой задаче такой защиты не даёт. Решение «не выполнять этот запуск» должно передаваться engine явно и не зависеть от повторного совпадения статуса после чужого Restart.

Тест считает вызовы processBatch, а не моделирует порчу данных этим callback. Он проверяет обход запрета запуска. На in-memory пропущен: нужны независимые транзакции PostgreSQL.
