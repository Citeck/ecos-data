# Общий пул id: один запрос вместо опроса со sleep

Отдельная тема от COREDEV-501, сделана в той же ветке по решению пользователя 2026-09-18
(«давай сделаем в этой»). Затрагивает `DbIdMappingService` и, через него, четыре таблицы-словаря:
`ed_record_ref`, `ed_attributes`, `ed_authorities`, `ed_workspace`.

## Что было

`DbDataServiceImpl.saveAtomicallyOrGetExistingByExtId`:

1. `INSERT ... ON CONFLICT (__ext_id) DO NOTHING RETURNING id` в **автономной транзакции**
   (`TxnContext.doInNewTxn` + `withTransaction(requiresNew = true)`);
2. если вернулось пусто — опрос таблицы в отдельной читающей транзакции: до 5 раз,
   `Thread.sleep(400)` между попытками;
3. весь цикл — до 3 раз, затем `error("Entity insertion failed...")`.

Худший случай — 6 секунд сна внутри пользовательского запроса.

Опрос там был не от робости: при конфликте `DO NOTHING` не возвращает ничего, а строка чужой
незакоммиченной транзакции невидима для читателя и **не может быть заблокирована** — `SELECT`, в том
числе `FOR UPDATE`, ждать на ней не умеет. То есть «вставить, потом посмотреть» действительно
вырождается в опрос.

## Замеры на `postgres:12.6`

Конкурент держит транзакцию открытой 5 с после своей вставки:

| запрос | поведение |
|---|---|
| `ON CONFLICT (ext) DO NOTHING RETURNING id` | ждал 4002 мс, вернул **0 строк** |
| `ON CONFLICT (ext) DO UPDATE SET ext = EXCLUDED.ext RETURNING id` | ждал 4003 мс, вернул **id победителя** |
| то же, но конкурент делает `ROLLBACK` | ждал 3003 мс, **вставил свою строку** и вернул её id |

Оба варианта ждут; возвращает id только `DO UPDATE`. То же самое проверено на **`postgres:18`**
(конкурент держал транзакцию 4 с, запрос ждал 2984 мс и вернул id победителя) — поведение не
версионное.

## Что стало

`DbEntityRepo.insertOrGetByExtId(context, entity, extraLongColumns)` — один запрос, всегда id: свой
при вставке, чужой при конфликте, плюс значения запрошенных колонок той же строки. `saveAtomicallyOrGetExistingByExtId` сжался до одной автономной транзакции и
одного вызова; опрос, sleep'ы и трёхкратный retry удалены. In-mem бэкенд повторяет семантику:
ждать ему не на чем, `InMemDataSource` сериализует пишущие транзакции.

**Автономная транзакция осталась и должна остаться.** Две причины, обе записаны в коде:
выданный id — обещание другим транзакциям, в том числе уже записавшим его в свои строки, поэтому
откат вызывающего не должен его отбирать; и блокировка строки, которую берёт `DO UPDATE`, живёт до
конца транзакции — внутри пользовательской мутации она попала бы в те же циклы блокировок, что и
`ed_associations`.

**Цена:** конфликт теперь пишет — мёртвый кортеж на каждое столкновение. Доходит до этого только
настоящая гонка: сначала Caffeine-кеш, потом `SELECT` в `getIdsByExtIds`.

## Цена в круговых обращениях

| путь | было | стало |
|---|---|---|
| реф уже в кеше | 0 запросов | 0 |
| реф есть в таблице, кеш промахнулся | 1 `SELECT` | 1 `SELECT` |
| рефа нет — регистрация | `BEGIN`/`INSERT`/`COMMIT` | то же |
| конфликт с закоммиченной строкой | + опрос в отдельной транзакции (≥3 обращения) | 0 дополнительных |
| конфликт с открытой транзакцией | ожидание + опрос + до 5×400 мс сна, до 3 циклов | ожидание внутри того же запроса |

Редирект (`__moved_to`) возвращает сам `RETURNING`, поэтому дочитывания строки нет ни на одном пути.
Для этого в `DbDataSource` добавлен `updateReturning`: `update` читает только первую колонку, а
гонять запись через `query` нельзя — в метриках и в логе медленных запросов она была бы помечена как
`SELECT`.

## Попутно исправленный дефект

Конфликтный путь возвращал **физический** id строки, в которую попал. `ed_record_ref` хранит
редиректы: перемещение id записи оставляет надгробие под старым текстом с `__moved_to` на живую
строку. Если надгробие появилось между поиском и вставкой, вызывающий получал id надгробия и писал
его в свои связи — все последующие читатели уходили на старый текст ссылки. Теперь `__moved_to` возвращается
тем же `RETURNING` — только для таблиц, у которых редиректы вообще есть (`movedToGetter != null`), и
`DbIdMappingService` резолвит эффективный id без дополнительного чтения.

## Тесты

Покрытия у этого места не было вовсе: ни трёх транзакций, ни sleep'ов, ни шестисекундного отказа, ни
самого контракта. Теперь в `DbIdMappingCacheTest`:

| тест | что фиксирует |
|---|---|
| `aReferenceCreatedByAnotherWriterInsideTheRaceIsNotCreatedTwiceTest` | двое просящих один реф получают один id |
| `aReferenceRegisteredByATransactionThatRolledBackKeepsItsIdTest` | id переживает откат попросившей транзакции |
| `aCollisionWithAnOpenTransactionWaitsForItRatherThanPollingTest` | столкновение с открытой транзакцией **ждёт** её |
| `theLoserOfTheRaceGetsTheIdTheReferenceResolvesToTest` | проигравший получает id, в который реф резолвится |

Честность проверена: последний до правки падал (`expected: 1L but was: 2L` — id надгробия). Три
первых — характеризационные, они зелёные и до, и после: контракт не менялся. Прямо: тест про
ожидание **не различает** `DO NOTHING` + опрос и `DO UPDATE` — оба ждут; он ловит реализацию, которая
не ждёт, дублирует строку или падает.

Гонка ставится барьером `DbStorageWriteBarrier` (он уже перехватывает эту вставку), конкурент живёт в
отдельном потоке: `TxnContext.doInNewTxn` не выдаёт нового JDBC-соединения. На in-mem три таких теста
пропускаются по `assumeConcurrentTransactionsSupported` — он сериализует транзакции на одном локе.

Полный прогон: `ecos-data-sql` 140/0/0, `ecos-data-sql-pg` 948/0 (1 skipped), `ecos-data-inmem`
1825/0 (88 skipped).

## Что стоит держать в голове дальше

- Уровень изоляции нигде не задаётся, то есть везде `READ COMMITTED` (проверено грепом:
  `setTransactionIsolation` в платформе не вызывается).
- `xmax = 0` как признак «строку вставили, а не обновили» на `12.6` работает (проверено), но это
  деталь реализации; он не понадобился, потому что `RETURNING` отдаёт нужную колонку напрямую.
